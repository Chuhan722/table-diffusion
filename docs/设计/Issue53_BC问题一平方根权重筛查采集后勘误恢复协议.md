# Issue #53 B+C 问题一：平方根权重筛查采集后勘误恢复协议

## 1. 触发原因

执行协议
`3330da8dd3bc9fbe264848491414893143f17da13cf42e3438611c24041d359a`
下的两条 GPU 轨迹已全部完成 case 级原子写入，但旧 Stage 6E
适配校验器在最终收口时仍断言：

```text
state_evaluation_count == applied_rounds + 1
```

生成器的实际语义与已有 Stage 6E 采集后勘误一致：

```text
state_evaluation_count == max(1, applied_rounds)
```

两个 case 都只在这一条历史断言上失败。该错误发生在生成全部
结束之后，不改变终表、检查点向量、转移时钟、停止决定、随机流或
平方根权重诊断。

- 原生成提交：`1ad75f9778969b8d0592f02601a0b596dbaa20e5`。
- 原 runner SHA-256：
  `6ad50b81c1c7c7d9043124b50da11b3540cde712d47546a5ce9c809631ff12e4`。
- 原暂存目录：
  `.local_rtx4090.staging-iencmg3i`。

  `fe29604c2ab5e6db71577686cd8d4b3d8b02198086cd1279df32196d30cfa07d`。
- 两个 case 的 manifest、终表、检查点和转移审计共 8 个文件，其
  SHA-256 与字节数全部写入机读恢复协议。

## 3. 恢复边界

- 恢复器只允许接受上述冻结字节；任一文件缺失、多出或变化立即
  失败。
- 唯一语义勘误是状态评价次数公式。为了复用旧校验器，恢复器只在
  内存中构造一份 `applied_rounds + 1` 的代理行；冻结原行绝不回写。
- 其余 Stage 6E 行校验以及平方根权重、`8*K`、停止、身份、顺序、
  随机流和哈希护栏全部保留。
- 不删除、不重跑任何 case，不调用生成器，不读取原始参考表，不计算
  或解释 L1、分箱、查询阶数以及方法优劣。
- 检查点文件只校验协议身份、状态位置、字段集合和向量长度，不使用
  其中的查询答案或质量数值得出结论。
- 恢复器只补写结构性 shard/collection 报告，并原子合并现有两个
  case。

## 4. GPU 监控证据限制

原 runner 在两条任务完成后、写 shard report 之前触发行校验错误，
因此其内存中的 GPU monitor 样本没有落盘。监督执行期间另有多次只读
`nvidia-smi` 观察，确认了物理 GPU 1、约 11.4 GiB 显存使用以及正常
利用率和温度。恢复报告必须明确记录：

- 原 runner monitor 样本未持久化；
- 监督观察样本的确切内容与来源；
- 监督样本不是原 runner 样本，不能将执行监控表述为完整。

执行前 GPU 身份/空闲 preflight、case 中的 `cuda:0` 身份以及监督样本共同
支持硬件身份，但不伪造已丢失的原 monitor 序列。

## 5. 发布与后续

恢复后的 collection 继续绑定原科学协议、原执行协议、原 runner、原
生成提交和两个原始 case；另加恢复协议、恢复代码、恢复提交以及监控
限制字段。collection 本身仍不得发布质量结果。

恢复完成后只报告 collection SHA-256 并停止。离线评价仍需下一步单独
授权；恢复不授权自动评价、扩大种子、修改参数、推送或 PR 操作。
