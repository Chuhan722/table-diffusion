# Issue #53 B+C 问题一：R8 筛查采集后勘误恢复协议

## 1. 触发原因

执行协议 `8c662f6d0568525b62a6002f3be4913a3334b432bde91faaa70d5b58e6606a4a`
下的四条 GPU 轨迹已全部完成 case 级原子写入，但旧 Stage 6E 适配校验器在
最终收口时仍断言：

```text
state_evaluation_count == applied_rounds + 1
```

生成器实际冻结语义以及既有 Stage 6E 后采集勘误均为：

```text
state_evaluation_count == max(1, applied_rounds)
```

四个 case 都只在这一旧断言上失败。该错误发生在生成全部结束之后，不改变
终表、检查点向量、转移时钟、停止决定、随机流或 R8 权重诊断。

## 2. 恢复边界

- 冻结原暂存目录、暂存清单以及四个 case 的 manifest、终表、检查点和转移
  审计文件的 SHA-256 与字节数。
- 恢复器只允许接受上述冻结字节；任一文件缺失或变化立即失败。
- 唯一语义勘误是状态评价次数公式。其余旧 Stage 6E 行校验和 R8 专用权重、
  `8*K`、停止、身份、配对及哈希护栏全部保留。
- 不删除、不重跑任何 case，不调用生成器，不读取原始参考表，不计算或解释
  L1、分箱、查询阶数及方法优劣。
- 恢复器只补写结构性 shard/collection 报告并原子合并现有四个 case。

## 3. GPU 监控证据限制

原 runner 在四条任务完成后、写 shard report 之前触发行校验错误，因此其
内存中的原始 GPU monitor 样本没有落盘。监督执行期间另有多次只读
`nvidia-smi` 观察，持续确认物理 GPU 1、两个工作进程、约 21.8 GiB 总显存
以及正常利用率/温度。恢复报告必须同时记录：

- 原 runner monitor 样本未持久化；
- 监督观察样本的确切内容与来源；
- 该限制不能被表述为原 runner 监控完整。

执行前内部 GPU 身份/空闲 preflight、case 中的 `cuda:0` 身份以及监督样本
共同支持硬件身份，但不伪造丢失的原始 monitor 序列。

## 4. 发布与后续

恢复后的 collection 继续绑定原生成协议、原 runner、原生成提交和四个原始
case；另加恢复协议、恢复代码、恢复提交及监控限制字段。collection 本身仍
不得发布质量结果。

恢复完成后先报告 collection SHA-256 并停止。离线评价仍需用户下一步指示；
恢复不授权自动评价、五种子确认、参数修改、推送或 PR 操作。
